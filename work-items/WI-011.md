## CADRAGE

Goal:
Améliorer la fluidité visuelle et ergonomique de la vue **Sprint actif** en rationalisant le scroll vertical. Aujourd'hui, la vue cumule le scroll de page et les scrolls internes de colonnes Kanban (`.board-col-body`), ce qui produit une expérience peu naturelle sur écran desktop type MacBook 15 pouces : ascenseurs multiples, wheel/trackpad qui change de zone selon le pointeur, lecture moins fluide du sprint.

Persona impact:
- **Arnaud / utilisateur Atelier** — la vue Sprint actif doit être plus lisible et plus agréable à parcourir, sans avoir à viser précisément une colonne pour scroller.
- **Claude Code / Codex** — la refactor WI-010 doit permettre une intervention plus courte et plus sûre : périmètre CSS/layout + rendu `renderBoard`, avec DnD conservé et tests ciblés.
- **Utilisateur final** — aucun changement métier attendu : mêmes items, mêmes statuts, mêmes filtres, même drag & drop, même clôture de sprint.

Context:
- ATE-30 est déjà présent dans l'app comme item en cours : "Rationaliser la vue de sprint et le scroll vertical de la vue".
- Captures Arnaud du 03/05/2026 sur production v0.19.0 : la vue affiche simultanément un scroll de page et des scrolls internes dans les colonnes `À faire`, `En cours`, `Terminé`.
- Le CSS actuel impose `max-height: calc(100vh - 220px)` sur `.board-col` et `overflow-y: auto` sur `.board-col-body`, donc chaque colonne devient une zone de scroll indépendante.
- `renderBoard()` rend le sprint header puis `#kanbanBoard` avec 3 colonnes ; le DnD board cible `.board-col[data-status]` et `.board-col-body`.
- WI-010 a sorti les primitives items / drag-drop / calendar, ce qui doit réduire le contexte nécessaire, mais la vue Sprint actif reste une surface centrale à tester soigneusement.

Constraints:
- **Comportement métier constant** : pas de changement data model, statuts, filtres, compteurs, estimation, sprint actif ou clôture.
- **DnD board préservé** : drag card `todo → doing → done` doit rester stable après changement de layout/overflow.
- **UX desktop prioritaire** : cibler au minimum les viewports équivalents MacBook 15 pouces et desktop large. Mobile/tablette seulement en non-régression basique sauf arbitrage PRD contraire.
- **Pas de refonte Kanban complète** : pas de nouvelle navigation, pas de virtualisation, pas de redesign global de la sidebar ou du header.
- **Changement borné** : privilégier CSS/layout et ajustement léger du markup si nécessaire ; escalader si la solution impose une restructuration lourde.

Out of scope:
- Nouvelle feature sprint.
- Refonte complète de la page backlog/sprint/archive.
- Changement de design system général.
- Réécriture DnD.
- Optimisation de performance non liée au scroll/layout.
- Responsive mobile avancé.

Open questions:
1. **Scroll cible** : veut-on un scroll unique de page pour toute la vue Sprint actif, ou un scroll unique de zone board sous un header sprint éventuellement sticky ?
2. **Headers colonnes** : les titres `À faire / En cours / Terminé` doivent-ils rester visibles en sticky pendant le scroll long ?
3. **Colonnes vides / courtes** : faut-il garder des colonnes visuellement alignées en hauteur, ou accepter une hauteur naturelle par contenu pour supprimer les ascenseurs internes ?
4. **Viewport de validation** : quelle taille reproduit le mieux la gêne observée ? Proposition initiale : `1440x900`, `1512x982`, et desktop large `1996x1238` vu dans les captures.
5. **Scope CSS partagé** : la rationalisation doit-elle s'appliquer uniquement à `state.activeView === 'board'`, ou aussi aux sections sprint dans le backlog si elles héritent de styles proches ?

Decisions:
1. ATE-30 ouvert comme WI UX/layout post WI-010, avec objectif explicite de tirer profit de la modularisation sans relancer une refonte.
2. Mode `STANDARD` retenu : surface utilisateur centrale + DnD + besoin de validation visuelle.
3. Risk `MEDIUM` : risque principal de régression layout/scroll/DnD, pas de risque data ou sécurité identifié.
4. Cible produit préférée au cadrage : réduire les scrolls imbriqués et tendre vers **un scroll principal lisible** pour la vue Sprint actif.
5. Le PRD devra inclure au moins une hypothèse de layout validable par captures avant/après sur les viewports de référence.

Objective:
Rationaliser la vue Sprint actif en alignant son scroll sur le **pattern Kanban industrie (Jira/Trello)** : board prend la hauteur viewport restante, scroll INTERNE par colonne (status quo conservé), **suppression du scroll de page parent** qui crée la confusion actuelle. UX desktop fluide, DnD préservé, comportement métier inchangé. Cible v0.20.0.

Current behavior:
- `.board-col` (CSS ligne ~590 d'`index.html`) impose `max-height: calc(100vh - 220px)` (heuristique fragile dépendante de la hauteur des autres éléments).
- `.board-col-body` (CSS ligne ~617) a `overflow-y: auto` → scroll interne par colonne (correct dans le pattern Kanban).
- **Mais** le container parent de la vue board ne contraint pas sa propre hauteur → la page entière peut scroller VERTICALEMENT en plus, créant un mix page+colonne. Le wheel/trackpad change de zone selon le pointeur (frustration Arnaud).
- Headers de colonnes (`.board-col-head` "À faire / En cours / Terminé" + compteur) défilent avec le contenu de leur colonne pendant le scroll interne, perdant leur fonction de repère.
- Sprint header (`.sprint-header` ligne ~3882) défile avec la page (puisque la page elle-même scrolle), perdant la vision globale d'avancement.

Target behavior (v0.20.0, voie B Kanban — corrigé PRD#3) :
- **Classe de contexte `.view-board`** posée sur `.main` (ou `#viewContent`) quand `state.activeView === 'board'`. Toutes les règles CSS de ce WI sont **strictement préfixées** par cette classe pour ne pas impacter backlog/archive/calendar (P2#4).
- **`.main.view-board { overflow-y: hidden }`** : la zone principale de l'app ne scrolle plus verticalement quand on est sur la vue board. Le scroll context vertical pour le contenu = uniquement `.board-col-body` (status quo).
- **Layout flex column** sur le chemin `.main.view-board → #viewContent → .sprint-header + .board` : `.sprint-header` prend sa hauteur naturelle, `.board` prend `flex: 1` (hauteur restante). **Pas de magic number type `calc(100vh - 220px)`** (P2#5).
- **Scroll interne `.board-col-body`** conservé tel quel : `overflow-y: auto` (status quo). C'est l'**unique** scroll context interne (P1#2 tranché). `.board-col` ne devient PAS scrollable.
- **`.board-col-head`** reste sibling de `.board-col-body` dans `.board-col`, **hors zone scrollée** : visible naturellement en haut de la colonne, **pas besoin de `position: sticky`**. Plus simple, évite tout risque de stacking context cassé.
- **`.board { align-items: stretch }`** : les 3 `.board-col` prennent la même hauteur (= hauteur du `.board` container). Suppression du `max-height: calc(100vh - 220px)` arbitraire (status quo CSS) au profit du flex stretch parent.
- **DnD board strictement préservé** : `.board-col[data-status]` + `.board-col-body` restent les drop targets. Listeners shell `attachDragDrop()` inchangés. Le scroll interne par colonne est déjà compatible avec dragover/drop (status quo confirmé sur 17 tests `calendrier-dnd.spec.js`).
- **Comportement métier inchangé** : items, statuts, filtres, compteurs, estimation, clôture sprint, mode test — strictement identique.

User stories :
- **US1 — Scroll Kanban prévisible desktop**. En tant qu'Arnaud sur MacBook 15", quand je consulte le sprint actif, je veux que le wheel/trackpad ne scrolle QUE le contenu de la colonne survolée (pas une page parent en plus). Pattern familier Jira.
- **US2 — Vision globale persistante**. En tant qu'Arnaud, je veux que le sprint header (avancement, bouton "Terminer le sprint") et les titres de colonnes restent toujours visibles, sans dépendre de ma position de scroll.
- **US3 — DnD préservé**. En tant qu'Arnaud, après le refactor, je veux pouvoir drag&drop sans nouveau bug ni régression.
- **US4 — Hauteurs colonnes alignées**. En tant qu'Arnaud, je veux que les 3 colonnes aient la même hauteur visuelle (pattern Jira), même si leur contenu diffère.

Acceptance criteria :

### AC1 — `.main` ne scrolle pas verticalement sur vue board (corrigé P1#1 Codex)
Given un utilisateur sur la vue Sprint actif (`state.activeView === 'board'`) avec un sprint actif et au moins 15+ items dans une colonne (overflow garanti)
When le DOM est rendu et le test inspecte le scroll context vertical réel
Then **`.main.view-board` (ou `.main` quand `state.activeView === 'board'`) doit avoir `scrollHeight ≤ clientHeight + epsilon`** (pas de scroll vertical sur la zone principale). Vérification via `getComputedStyle` ET `Element.scrollHeight/clientHeight`.
And **au moins une `.board-col-body` doit avoir `scrollHeight > clientHeight`** (scroll interne attendu sur la colonne longue).
And **`document.scrollingElement.scrollTop === 0`** reste vrai en permanence sur vue board (le `body` non plus ne scrolle pas).
When l'utilisateur scrolle verticalement (wheel/trackpad) depuis l'extérieur d'une colonne (sprint header ou entre colonnes)
Then aucun défilement vertical ne se produit sur `.main` ni sur `body`.
When il scrolle verticalement depuis l'intérieur d'une `.board-col-body`
Then **seul le contenu de cette colonne défile** ; `.main` reste à `scrollTop === 0`.

### AC2 — Sprint header visible en permanence (statique)
Given la vue Sprint actif rendue
When l'utilisateur défile dans n'importe quelle colonne
Then **le `.sprint-header` (nom sprint + dates + barre progression + bouton "Terminer le sprint") reste visible** en haut de la vue, par construction du layout flex (pas besoin de `position: sticky` puisque la page elle-même ne scrolle pas).
And la barre de progression continue d'afficher le pourcentage à jour.
And le bouton "Terminer le sprint" reste cliquable à tout moment.

## PATCH_NOTES

## 🎯 Vue Sprint actif — un seul scroll, pattern Kanban (ATE-30)

La vue **Sprint actif** était jusqu'ici saccadée sur écran desktop : la page entière scrollait verticalement pendant que chaque colonne Kanban (`À faire / En cours / Terminé`) scrollait aussi de son côté, et le wheel/trackpad changeait de zone selon où était le pointeur. Cette release rationalise tout ça avec le pattern Kanban classique (Jira / Trello) : **un seul scroll par colonne**, board calé sur la hauteur viewport, plus de scroll de page parent.

## ✨ Ce qui change pour toi

- Le wheel/trackpad **scrolle uniquement la colonne** survolée — plus de bascule imprévisible vers le scroll de page.
- Le **sprint header** (nom, dates, barre de progression, bouton "Terminer le sprint") reste toujours visible en haut, même si tu défiles dans une longue colonne `À faire`.
- Les **headers de colonnes** (`À faire 12 / En cours 3 / Terminé 8` …) restent visibles dans leur colonne — tu sais toujours où tu es.
- Les **3 colonnes ont la même hauteur visuelle**, alignées sur le viewport, peu importe que l'une ait 20 cartes et l'autre 0.
- Aucun changement métier : items, statuts, filtres, drag & drop, clôture sprint — tout strictement identique.

## 🛠️ Détails techniques

- **Classe de contexte `.view-board`** posée sur `.main` quand `state.activeView === 'board'` (retirée sur backlog/archive/calendar). Toutes les nouvelles règles CSS sont strictement préfixées par cette classe, **zéro fuite** vers les autres vues.
- **Layout grid + flex** sur `.main.view-board → #viewContent → .sprint-header + .board` pour que `.board` prenne la hauteur restante après breadcrumb / page-header / filters-bar / sprint-header. **Aucun magic number** type `calc(100vh - 220px)` (l'ancien `max-height` arbitraire sur `.board-col` est supprimé).
- **`.main.view-board { overflow-y: hidden }`** : la zone principale ne scrolle plus verticalement sur la vue board. Le scroll context vertical reste exclusivement `.board-col-body` (status quo conservé). Pas de `position: sticky` introduit (header visible par DOM sibling, plus simple).
- **Timer anti-click DnD** ajusté de 100ms → 150ms dans `js/drag-drop.js` (compatibilité Playwright `dragTo` avec le nouveau layout grid).
- **DnD board strictement préservé** : listeners shell sur `.board-col[data-status]` + `.board-col-body` inchangés ; le module `js/drag-drop.js` (livré WI-010) reste intact.
