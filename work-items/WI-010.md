## CADRAGE

Goal:
Réduire la friction de développement et de tests introduite par la feature **Calendrier** avant d'ajouter de nouvelles features Atelier. L'objectif n'est pas de changer l'UX visible, mais de stabiliser les primitives internes qui rendent aujourd'hui les évolutions plus coûteuses : lookup item multi-projets, mutations item, drag & drop, waits Playwright, rendu calendrier, valeurs par défaut des items.

Persona impact:
- **Arnaud** — gain indirect mais important : les prochains WI doivent être plus fluides, moins sujets aux flakes Playwright, et moins coûteux à faire évoluer avec Claude/Codex. Moins de boucles "fix test-side / fix app" et moins de regressions calendrier quand on touche au backlog, board ou activité.
- **Claude Code / Codex** — gain de maintenabilité : surfaces plus petites à raisonner, invariants explicites, tests plus déterministes.
- **Utilisateur final Atelier** — pas de changement fonctionnel attendu, sauf meilleure stabilité et absence de régression.

Context:
- Depuis la feature calendrier, `index.html` est devenu plus complexe : environ 5 800 lignes, avec storage/sync, rendu, calendrier, DnD, activité et modals dans un seul fichier.
- Le calendrier a introduit une rupture d'invariant : les vues historiques (`backlog`, `board`, `archive`, sidebar) raisonnent via `getActiveClient()`, alors que le calendrier est **multi-projets** et doit transporter `clientId` dans des copies d'items.
- Le DnD a maintenant plusieurs protocoles parallèles : `dragItemId`, `calendarDragItem`, `dragJustHappened`, gardes anti-cross-feature, `setTimeout(..., 100)`.
- Les tests calendrier passent, mais leur coût et leur fragilité augmentent : helpers locaux dupliqués, `waitForTimeout(150)` / `waitForTimeout(120)` pour attendre `loadState`, `saveState`, `render`, et simulation DnD custom.
- WI-009 (`actualHours`) a révélé un manque de factory item : le champ optionnel oublié à la création inline a créé un phantom event `undefined → 0`, corrigé en ajoutant `actualHours: 0`.
- Review Codex ciblée du 02/05/2026 : suites `calendrier.spec.js`, `calendrier-dnd.spec.js`, `duree-reelle.spec.js` lancées avec succès après autorisation serveur local : **40 passed (37.6s)**. Le problème identifié est donc surtout **architecture / maintenabilité / flakiness potentielle**, pas un bug fonctionnel immédiat.

Constraints:
- **Zéro changement UX volontaire** : refactor/stabilisation à comportement constant.
- **Pas de nouveau domaine fonctionnel** dans ce WI. Toute amélioration produit (nouvelle vue, nouveau filtre, stats avancées) est hors-scope.
- **Préserver les données existantes** : aucun changement de format Gist non rétro-compatible.
- **Préserver la suite Playwright** : toute refactorisation doit garder ou améliorer la couverture existante.
- **Refactor incrémental** : éviter une réécriture massive de `index.html`. Toucher des primitives ciblées et vérifier chaque étape.
- **Limiter les risques DnD** : board, backlog, sidebar et calendrier doivent continuer à fonctionner.

Out of scope:
- Extraction complète de l'app en modules JS séparés / build system / framework.
- Migration React/Vue/Svelte.
- Refonte CSS ou design du calendrier.
- Nouvelles features calendrier.
- Optimisation micro-perf prématurée type virtualisation calendrier.
- Refonte du protocole Gist sync.
- Suppression du mode test ou changement profond du seed.

Open questions:
1. **Granularité du WI** : fait-on les 5 axes dans un seul WI STANDARD, ou faut-il splitter en 2 WI (`tests deterministes + factory` puis `DnD + calendrier view-model`) ?
2. **Tolérance au changement de code structurel** : accepte-t-on de déplacer des blocs de fonctions dans `index.html` sans changement fonctionnel pour regrouper les primitives (`item helpers`, `drag helpers`, `calendar`), ou limite-t-on aux extractions minimales ?
3. **Niveau de tests attendu** : suffit-il de la suite existante + quelques tests non-régression ciblés, ou veut-on ajouter des tests dédiés pour les nouvelles primitives pures via Playwright `page.evaluate` ?
4. **DnD** : doit-on viser une unification complète `dragContext` dans ce WI, ou seulement poser une couche compatible en gardant les anciens noms comme wrappers ?
5. **Waits Playwright** : peut-on ajouter des marqueurs test-only globaux (`window.__renderVersion`, `window.__lastSaveCompletedAt`) dans l'app, ou préfère-t-on des waits purement DOM/state côté tests ?

Decisions:
1. **ATE-31 créé comme WI technique de stabilisation post-calendrier** — demandé par Arnaud après WI-009, suite à la review Codex générale perf/cohérence/fluidité.
2. **Mode initial `STANDARD` / Risk MEDIUM** — scope transverse, touche DnD + tests + primitives item + calendrier. Le risque est surtout régression invisible/flaky tests, pas sécurité.
3. **Objectif comportement constant** — toute évolution UX détectée doit être explicitement justifiée ou sortie du WI.

Objective:
Stabiliser les primitives internes de l'app Atelier post-feature Calendrier, **sans changement UX**, et **réduire le contexte agent** nécessaire pour faire évoluer le code. Cible v0.19.0 stabilisation technique. 6 axes : (a) factory item canonique, (b) tests Playwright déterministes via marqueurs test-only globaux, (c) DnD unifié via `_dragContext` + helpers explicites, (d) view-model calendrier pur, (e) regroupement logique des helpers + extraction modulaire bornée (≤ 3 modules ES natifs), (f) documentation agent-context (carte des domaines + invariants transverses) pour que Claude/Codex chargent moins de code par WI futur. Aucun nouveau domaine fonctionnel.

Current behavior:
- **Factory item ad-hoc** : champs ajoutés au coup par coup au chemin de création inline (`actualHours: 0` ajouté en WI-009 après bug phantom event `undefined → 0`). Risque de récidive à chaque nouveau champ.
- **Tests calendrier flakys-prone** : `waitForTimeout(150)` / `waitForTimeout(120)` éparpillés pour attendre `loadState` / `saveState` / `render`. Helpers locaux dupliqués (ex. `simulateDnd` custom dans `calendrier-dnd.spec.js`).
- **DnD multi-protocoles** : `let dragItemId` (backlog/board), `let calendarDragItem` (calendrier), `let dragJustHappened` (anti-cross-feature), gardes `setTimeout(..., 100)` éparpillées. Variables lexicales globales sans contrat.
- **Calendrier view-model implicite** : items copiés avec `clientId` sans factory dédiée, lookup multi-projets via `state.clients.flatMap(...)` répété.
- **`index.html` 5800 lignes mono-fichier** : sections logiques (storage / render / DnD / modals / activity / calendrier) interleaved sans regroupement explicite, navigation cognitive coûteuse pour les agents qui chargent tout systématiquement.
- **Pas de carte de contexte agent** : Claude et Codex relisent souvent l'intégralité de `index.html` faute de doc qui guide vers les seules zones pertinentes par type de WI.

Target behavior (état attendu après ce WI) :
- **Factory item canonique `_buildItem(partial)`** : retourne un item avec **TOUS les champs trackables définis** (jamais `undefined`). Tous les chemins de création (form inline, demo seed, import via `_normalizeItem`) passent par cette factory ou par `_normalizeItem` qui pose les mêmes defaults (extraction d'un `_itemDefaults()` interne).
- **Tests déterministes** : marqueurs test-only `window.__appStateVersion` (incrément à chaque render) et `window.__lastSaveCompletedAt` (timestamp à chaque save async terminé), gatés par mode test / `__SKIP_SEED__`. Helpers Playwright `waitForRender(page, opts)` et `waitForSave(page, opts)` ajoutés à `tests/helpers.js`. ≥ 50% des `waitForTimeout` arbitraires des suites concernées remplacés.
- **`_dragContext` + helpers explicites** : objet global `_dragContext = { source: 'backlog'|'board'|'calendar', itemId, clientId, payload, startedAt }` posé via `startDrag(ctx)`, clear via `endDrag()`. Helpers `getDragItemId()`, `getCalendarDragItem()`, `didDragJustHappen()` exposés. Anciens `let dragItemId` / `let calendarDragItem` / `let dragJustHappened` synchronisés temporairement par `startDrag/endDrag` jusqu'à migration complète des call-sites vers les helpers (dans ce WI).
- **Calendrier view-model pur** : `_buildCalendarItems(state, filters)` retourne un tableau d'items annotés `{ ...item, clientId, clientName, clientKey, epicColor }`. Testable en isolation via `page.evaluate`. Invariants existants préservés (exclusion done, exclusion hors-mois, fallback gris epic orphelin, timezone-safe, tooltip `Client · Epic · Titre`).
- **Architecture cible : `index.html` shell + ≤ 3 modules ES natifs** : `js/items.js` (factory + clamp + normalize), `js/calendar.js` (view-model + helpers month/cell/today), `js/drag-drop.js` (`_dragContext` + helpers + DnD simulation/sync). Chargement via `<script type="module" src="js/items.js"></script>` (ou bundle implicite si nécessaire). Pas de framework, pas de bundler. État intermédiaire (partie inline + partie module) accepté pendant la migration.
- **Documentation agent-context** : `docs/agent-context.md` (ou section dédiée `README.md`) avec carte des domaines (`items`, `calendar`, `drag-drop`, `storage/sync`, `activity`), fichiers à lire selon le type de WI, invariants transverses obligatoires (validation `_normalizeItem`, `state.clients[*].items[*]` schéma, escapeHtml/Attr, mutation `state → saveState() → render()`). Objectif : règle "lire le module ciblé + le contrat partagé, pas tout le monolithe".

User stories:
- **US1 — Dev futur sans phantom events**. En tant que Claude/Codex/Arnaud futur dev, je veux qu'ajouter un nouveau champ optionnel à un item soit fiable et trivial : modifier la factory + le `_normalizeItem`, point. Pas de chasse au phantom event au premier `saveItemEdit`.
- **US2 — CI Playwright stable**. En tant que pipeline `npm test` (local ou CI futur), je veux que les suites passent de manière déterministe sans `waitForTimeout` arbitraires sujets à flake en environnement chargé.
- **US3 — DnD lisible**. En tant que dev qui touche au DnD, je veux raisonner sur un objet `_dragContext` unique + helpers explicites au lieu de naviguer entre `let` globaux et leurs gardes anti-cross-feature.
- **US4 — Calendrier testable**. En tant que dev qui touche au calendrier, je veux pouvoir lire son view-model en une seule fonction pure et tester ses invariants en `page.evaluate` sans monter de DOM.
- **US5 — Navigation `index.html` + modules**. En tant que dev qui ouvre l'app pour la 1ʳᵉ fois, je veux trouver chaque domaine dans son module dédié (`js/items.js`, `js/calendar.js`, `js/drag-drop.js`) avec un point d'entrée clair (`index.html` shell + commentaires d'ancrage).
- **US6 — Pipe agents avec contexte borné**. En tant que Claude/Codex sur un WI futur (ex. "ajouter une stat sprint"), je veux pouvoir charger uniquement `js/items.js` + le contrat `docs/agent-context.md` sans relire 5800 lignes de monolithe à chaque tour.

Acceptance criteria:

### AC1 — Factory item canonique `_buildItem`
Given un appel `_buildItem({ title: 'X', type: 'task', priority: 2, sprintId: 's1', client })`
When la fonction retourne l'item
Then **tous les champs trackables ont une valeur définie** (jamais `undefined`) : `id`, `num`, `title`, `type`, `priority`, `status`, `estimate`, `actualHours`, `dueDate`, `sprintId`, `epicId`, `createdAt`, `description`, `activity`.
And les valeurs par défaut respectent les invariants : `status: 'todo'`, `estimate: 0`, `actualHours: 0`, `dueDate: null`, `sprintId: null`, `epicId: null`, `description: ''`, `activity: []`, `createdAt: Date.now()`.
And **tous les chemins de création** d'item (formulaire inline, demo seed, import via `_normalizeItem`) construisent leurs items via `_buildItem` OU via `_normalizeItem` qui pose les mêmes defaults (factorisation `_itemDefaults()` interne acceptable).
And aucun phantom event d'activité (`undefined → 0` pour quelque champ optionnel) n'est généré au premier `saveItemEdit` d'un item nouvellement créé.
And **trois tests dédiés** (PLAN_REVIEW Codex test gaps) : (a) shape complète via `page.evaluate(() => _buildItem({ title: 'T' }))`, (b) item créé via UI form inline (test E2E click + verify), (c) item importé via `_normalizeItem` (test `page.evaluate` avec input partiel).

### AC2 — Marqueurs test-only globaux + helpers Playwright déterministes
Given le mode test ou `window.__SKIP_SEED__` actif
When `render()` complète
Then `window.__appStateVersion` est incrémenté de 1.
When `saveState()` async complète (Promise resolved post-IndexedDB write)
Then `window.__lastSaveCompletedAt = Date.now()`.
And ces marqueurs sont **strictement gatés** : `undefined` en mode normal (production app, sans `__SKIP_SEED__` ni mode test).
And deux helpers ajoutés à `tests/helpers.js` : `waitForRender(page, { from } = {})` (attend `__appStateVersion > from`) et `waitForSave(page, { from } = {})` (attend `__lastSaveCompletedAt > from`).
And **au moins 50%** des `waitForTimeout(150)` / `waitForTimeout(120)` des suites `tests/calendrier*.spec.js` + `tests/persistance.spec.js` + autres suites touchant render/save sont remplacés par ces helpers.
And **un test dédié** (PLAN_REVIEW Codex test gaps) vérifie que `window.__appStateVersion` et `window.__lastSaveCompletedAt` sont `undefined` en mode normal (sans `__SKIP_SEED__`, sans `atelier-mode-test`).

### AC3 — `_dragContext` + helpers explicites + migration call-sites
Given une opération de drag depuis `backlog`, `board`, ou `calendar`
When le drag démarre
Then un objet global `_dragContext = { source: 'backlog'|'board'|'calendar', itemId, clientId, payload, startedAt }` est posé via `startDrag(ctx)`.
And **trois helpers explicites** sont exposés et utilisés par tous les call-sites internes : `getDragItemId()`, `getCalendarDragItem()`, `didDragJustHappen()`.
And les anciens `let dragItemId` / `let calendarDragItem` / `let dragJustHappened` sont **synchronisés temporairement** par `startDrag(ctx)` et `endDrag()` (assignation explicite) **uniquement** pour les call-sites externes/legacy non encore migrés. Ils sont marqués `// @deprecated — utiliser getDragItemId() / getCalendarDragItem() / didDragJustHappen()` dans commentaires.
And **tous les call-sites internes de `index.html`** sont migrés vers les helpers explicites dans ce WI (suppression de toutes les références directes `dragItemId` / `calendarDragItem` / `dragJustHappened` côté code app, sauf déclarations + sync dans `startDrag/endDrag`).
And `endDrag()` clear `_dragContext` ET les `let` deprecated en cohérence.
And **aucune régression DnD** : tests existants `calendrier-dnd.spec.js`, sections board de `backlog.spec.js`, drag inter-sprints continuent à passer.
And **un test dédié** (PLAN_REVIEW Codex test gaps) vérifie le DnD sur les 3 sources (backlog/board/calendar) avec **attente déterministe** via `waitForRender` au lieu de `waitForTimeout`.

### AC4 — Calendrier view-model pur `_buildCalendarItems`
Given une vue calendrier rendue avec `state` + filtres `{ month: 'YYYY-MM', type?, priority?, projectId?, epicId? }`
When `_buildCalendarItems(state, filters)` est appelé
Then la fonction retourne un **tableau pur** d'items annotés `{ ...item, clientId, clientName, clientKey, epicColor }` ; aucune mutation du `state` original.
And la pureté est **vérifiée par snapshot** : `JSON.stringify(state)` avant et après l'appel sont identiques (test dédié PLAN_REVIEW Codex test gaps).
And la fonction est **testable en isolation** via `page.evaluate(({ filters }) => _buildCalendarItems(state, filters), { filters })`.
And les invariants existants sont **préservés et validés par les tests `calendrier.spec.js` actuels** : exclusion items `done`, exclusion items hors-mois, fallback couleur grise pour epic orphelin, timezone-safe, tooltip "Client · Epic · Titre".
And ≥ 1 nouveau test dédié vérifie la pureté + un invariant clé via `page.evaluate`.

### AC5a — Regroupement logique intra-fichier (peut suffire si AC5b non retenu)
Given le fichier `index.html` actuel ~5800 lignes
When le refactor de regroupement est terminé
Then **3 sections contigues** sont marquées par commentaires d'ancrage en majuscules :
- `=== ITEM HELPERS ===` (factory `_buildItem`, `_normalizeItem`, `_clampNumber`, `_clampInt`, `_clampString`, `_normalizeChangeFieldValue`, `_itemDefaults` si extraction interne)
- `=== DRAG CONTEXT ===` (`_dragContext`, `startDrag`, `endDrag`, helpers `getDragItemId/getCalendarDragItem/didDragJustHappen`, anciens `let` deprecated)
- `=== CALENDAR VIEW-MODEL ===` (`_buildCalendarItems`, helpers month/cell/today, lookup multi-projets)
And ces ancres servent de point d'entrée pour les agents (Claude/Codex) qui cherchent un domaine spécifique.

### AC5b — Extraction modulaire bornée (≤ 3 modules ES natifs) + compat handlers inline (révisé PLAN_REVIEW#2)
Given que AC5a est satisfait et que le spike compat ES modules natifs (AC10) est GO
When l'extraction modulaire est exécutée
Then **jusqu'à 3 fichiers modules maximum** sont créés dans `js/` :
- `js/items.js` — exporte `buildItem`, `normalizeItem`, `clampNumber/Int/String`, `itemDefaults`, `normalizeChangeFieldValue`.
- `js/calendar.js` — exporte `buildCalendarItems`, helpers month/cell/today.
- `js/drag-drop.js` — exporte `dragContext` (state local au module), `startDrag`, `endDrag`, `getDragItemId/getCalendarDragItem/didDragJustHappen`.
And `index.html` reste **shell d'accueil** : déclarations `<script type="module" src="js/items.js"></script>` (ou équivalent), points d'entrée explicites.
And **règle architecture (PLAN_REVIEW#2 refinement)** : *les modules exportent des primitives de domaine (factory, view-model, helpers purs ou state local circonscrit) ; le shell `index.html` orchestre le DOM, le `state` global et les handlers historiques jusqu'à migration explicite*. Pas de module qui importe ou mute le `state` global sans contrat — si un module a besoin du state, il reçoit les données en paramètre OU expose des fonctions pures. Exception : `js/drag-drop.js` peut maintenir son propre state `dragContext` local au module.
And **état intermédiaire toléré** : du code qui n'est pas encore extrait reste inline dans `index.html` ; pas d'obligation de tout migrer en une seule passe.
And **pas de framework, pas de bundler** : ES modules natifs uniquement. Pas de Vite/Webpack/esbuild dans ce WI.
And **compat handlers inline (PLAN_REVIEW#2 P1 #2)** : aucune fonction appelée par HTML inline (`onclick="switchView(...)"`, `onchange="filterByPriority(...)"`, etc.) ni par tests Playwright (`page.evaluate(() => switchView())`) n'est perdue lors du passage en module. Trois stratégies acceptables (combinables) :
  - **(a) Garder dans le shell** : les handlers UI (`switchView`, `openItemDetail`, `saveItemEdit`, `cycleStatus`, `filterByPriority/Type/Project/Epic`, callbacks DnD) **restent en top-level dans `index.html`** (script classique, pas module). Les modules exportent uniquement des primitives métier appelées **depuis** ces handlers.
  - **(b) Pont `window.*` transitoire** : un handler inline migré en module est ré-attaché explicitement via `window.switchView = switchView;` dans le module ou dans un script-bridge inline. Liste exhaustive des ponts documentée dans `docs/spike-modules.md` (cf. AC10) pour traçabilité.
  - **(c) Migration `addEventListener`** : les handlers inline du domaine extrait sont remplacés par `addEventListener` dans le module lui-même. Plus propre mais coût de migration plus élevé.
And **inventaire pré-extraction obligatoire** : avant toute extraction, un inventaire des **top fonctions globales appelées par HTML inline ou par tests** est dressé (ex. `switchView`, `openItemDetail`, `saveItemEdit`, `cycleStatus`, `filterByPriority`, `confirmDeleteItem`, `dragStart/Over/Drop` callbacks, `setActiveSprint`, `clientActionMenu`). Cet inventaire vit dans `docs/spike-modules.md`. Toute fonction de l'inventaire qui devient inaccessible post-extraction = BLOCKER.
And si AC10 (spike compat) est NO-GO → AC5b skippée, seul AC5a appliqué, le WI reste valide avec regroupement intra-fichier.

### AC6 — Suite Playwright complète verte (révisé PLAN_REVIEW#2)
Given la suite `npm test` complète
When elle est lancée après le refactor (commit final avant MERGE_RELEASE)
Then **suite complète PASS** (toléré : flake pré-existant `calendrier-dnd:132` documenté en WI-009 si reproduction). **Total réel relevé et documenté dans `## TESTS.Notes`** (e.g. "146 + N nouveaux tests = total NNN PASS"), pas de chiffre figé `146/146` qui devient incohérent dès l'ajout de tests neufs (PLAN_REVIEW#2 P1 #4).
And **1 run complet `npm test` obligatoire** + **3 runs ciblés** des suites touchées si waits/DnD modifiés (`tests/calendrier*.spec.js`, `tests/duree-reelle.spec.js`, `tests/persistance.spec.js`, `tests/activite.spec.js` selon impact).
And les nouveaux tests dédiés primitives (factory shape + factory via UI + factory via import + view-model pureté + boot module + handler inline post-extraction + accès `window.__atelierInternals` test-mode + absence internals/hooks mode normal + DnD 3 sources déterministe + UI commands post-extraction) passent et apportent **5 à 10 tests neufs**.

### AC7 — Comportement UX strictement constant

## 🔧 Stabilisation interne post-calendrier (ATE-31)

Cette release est **purement technique** : aucun changement UX volontaire, aucun nouveau domaine fonctionnel. Elle prépare le terrain des prochaines évolutions Atelier en stabilisant les primitives internes qui rendaient les WI plus coûteux depuis l'ajout du calendrier (lookup multi-projets, mutations item, drag & drop multi-vues, attentes Playwright fragiles).

## 🏗️ Architecture — 3 modules ES natifs

Le shell `index.html` reste mono-fichier (~5640 lignes) et délègue désormais les **primitives métier pures** à 3 modules ES natifs chargés via `<script type="module">` (sans framework, sans bundler) :

- **`js/items.js`** — Factory item canonique `buildItem(partial)` qui garantit que les **14 champs trackables** sont toujours définis (jamais `undefined`). Évite les phantom events d'activité au premier `saveItemEdit` (cf. bug WI-009 `actualHours`).
- **`js/drag-drop.js`** — Contexte DnD unifié `_dragContext = { source, itemId, clientId, payload, startedAt }` + helpers explicites `startDrag/endDrag/getDragItemId/getCalendarDragItem/didDragJustHappen`. Remplace les 3 anciennes variables `let` globales du shell (`dragItemId`, `calendarDragItem`, `dragJustHappened`) par une source unique modulaire.
- **`js/calendar.js`** — View-model calendrier **pur** : `localDateKey`, `buildMonthCells`, `buildCalendarItems(state, filters)`, `indexCalendarItems`. Pureté garantie par snapshot `JSON.stringify(state)` identique avant/après l'appel.

Bridge `<script type="module">` (~ligne 2188 d'`index.html`) expose les primitives sur `window.*` (compat shell historique) + `window.__atelierInternals.*` (test-mode-gated pour `page.evaluate` Playwright).

## 🧪 Tests + helpers déterministes

- **Marqueurs test-only globaux** : `window.__appStateVersion` (incrément à chaque `render()`) et `window.__lastSaveCompletedAt` (timestamp à chaque save async terminé), **strictement gatés** mode test / `__SKIP_SEED__` (invisibles en production).

- **21 nouveaux tests E2E dédiés** (`tests/spike-modules.spec.js`) couvrant boot module, factory shape + UI + import, marqueurs test-only, DnD context multi-source + DnD DOM réel via `dragTo()`, view-model calendrier pureté.
