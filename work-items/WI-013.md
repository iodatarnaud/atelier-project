## PRD

Objective:
Étendre le board « Sprint actif » de 3 à 6 colonnes formant un pipeline de delivery Salesforce (`À faire → En cours → DEV → UAT → Go live → Terminé`), par ajout **additif** de 3 valeurs à l'enum statut (`dev` / `uat` / `golive`), avec scroll horizontal + largeur minimale de colonne, sans rupture de compat Gist.

Current behavior:
- Board = 3 colonnes HTML en dur (`todo`/`doing`/`done`) copiées-collées ([index.html:3994-4021](../index.html#L3994-L4021)), alimentées par 3 filtres `items.filter(i => i.status === …)` ([index.html:3971-3973](../index.html#L3971-L3973)).
- Enum statut à 3 valeurs : `STATUS_LABELS` ([index.html:2386](../index.html#L2386)), `STATUS_VALUES` ([index.html:2538](../index.html#L2538)), whitelist import coerce l'inconnu → `todo` ([index.html:2722](../index.html#L2722)), réplique `_ACTIVITY_STATUS_LABELS` ([index.html:5669](../index.html#L5669)).
- DnD générique : chaque `.board-col` lit `dataset.status` → écrit `item.status`, `completedAt` posé si `done` ([index.html:4603-4634](../index.html#L4603-L4634)).
- `cycleStatus()` défile le statut au clic-badge, ordre codé en dur ([index.html:3952](../index.html#L3952)).
- Pas de scroll horizontal board (3 colonnes tiennent) ; scroll vertical porté par `.board-col-body` (WI-011).

Target behavior:
- 6 colonnes rendues dans l'ordre `todo, doing, dev, uat, golive, done` (libellés `À faire, En cours, DEV, UAT, Go live, Terminé`), chacune avec compteur.
- Enum étendu additivement : `todo, doing, dev, uat, golive, done` dans `STATUS_LABELS`, `STATUS_VALUES`, `_ACTIVITY_STATUS_LABELS` + classes CSS `.status-<key>`.
- `done` reste le SEUL statut terminal (`completedAt`, archive, exclusion calendrier inchangés) ; `dev`/`uat`/`golive` = états en vol.
- DnD fonctionne entre les 6 colonnes via le mécanisme générique existant (aucune réécriture DnD).
- `cycleStatus()` défile les 6 statuts dans l'ordre du pipeline.
- Board `overflow-x: auto` : chaque colonne conserve une largeur minimale de 280px ; débordement → scroll horizontal du board uniquement (pas de scroll horizontal de la page).

User stories:
- US1 — En tant qu'Arnaud, je glisse une carte de UAT vers Go live quand le client a recetté, pour refléter l'étape réelle de livraison.
- US2 — Je vois mes 6 colonnes à une largeur lisible et je scrolle horizontalement quand elles dépassent l'écran.
- US3 — Un item passé en DEV/UAT/Go live est persisté puis rechargé au bon stade (compat Gist, round-trip export/import).
- US4 — Le clic sur le badge d'une carte fait défiler les 6 statuts du pipeline.

Acceptance criteria:

### AC1 — 6 colonnes ordonnées
Given un sprint actif contenant des items
When j'ouvre la vue « Sprint actif »
Then le board affiche 6 colonnes dans l'ordre À faire, En cours, DEV, UAT, Go live, Terminé, chacune avec le compteur d'items de son statut.

### AC2 — DnD entre stages persiste
Given une carte au statut `uat`
When je la glisse-dépose dans la colonne « Go live »
Then `item.status` devient `golive`, `saveState()` + `render()` s'exécutent, et après rechargement l'item réapparaît dans la colonne Go live.

### AC3 — Rétro-compat enum / round-trip Gist
Given un export JSON contenant un item `status: 'dev'` (et un `'uat'`, un `'golive'`)
When je réimporte ce JSON
Then les statuts `dev`/`uat`/`golive` sont préservés (non coercés en `todo`) — `STATUS_VALUES` étendu.

### AC4 — `done` reste seul terminal
Given une carte glissée vers « Terminé »
When le drop se produit
Then `completedAt` est posé ; pour un drop vers DEV/UAT/Go live `completedAt` n'est PAS posé ; le calendrier exclut uniquement `done` ([js/calendar.js:66](../js/calendar.js#L66)) ; l'archive ne contient que `done`.

### AC5 — Largeur minimale + scroll horizontal
Given les 6 colonnes et une largeur de contenu insuffisante
When la somme des largeurs (min 280px chacune) dépasse la zone board
Then le board scrolle horizontalement (`overflow-x: auto`), chaque colonne garde ≥ 280px, et la page (`.main` / `body`) ne scrolle pas horizontalement.

### AC6 — cycleStatus 6 états
Given une carte au statut `todo`
When je clique 6 fois sur son badge
Then le statut défile `todo → doing → dev → uat → golive → done → todo`.

### AC7 — Libellés & couleurs de badge
Given une carte à un statut `dev`/`uat`/`golive`
Then son badge affiche le libellé FR correct (« DEV » / « UAT » / « Go live ») via une classe `.status-<key>` avec une couleur lisible en thème clair ET sombre.

Out of scope:
- Sidebar repliable → WI-014 / ATE-35.
- Indicateurs chiffrés du sprint (% terminé, reste Xj) non retouchés malgré les stages non-`done`.
- Stages configurables par projet ; réordonnancement des colonnes ; automatisations de déploiement.
- Refonte du groupement de statuts des vues backlog / archive (au-delà de la cohérence des libellés).

Assumptions:
- Le DnD générique ([index.html:4603-4634](../index.html#L4603-L4634)) est réutilisable sans modification (câblage par `dataset.status`).
- Étendre `STATUS_LABELS` + `STATUS_VALUES` + `_ACTIVITY_STATUS_LABELS` + classes `.status-*` couvre tous les points de câblage statut ; à confirmer exhaustivement en IMPLEMENTATION (audit `grep 'todo'|'doing'|'done'`).
- `completeSprint()` ne clôt/archive que les items `done` ; les items non-`done` (dont dev/uat/golive) sont conservés/reportés à l'identique du comportement actuel — à vérifier en IMPLEMENTATION.

Risks:
- **Câblage statut incomplet** : oubli d'un des points (`STATUS_LABELS` vs `_ACTIVITY_STATUS_LABELS` vs `.status-*` CSS vs ordre `cycleStatus`) → statut affiché brut ou couleur manquante. Mitigation : audit `grep` exhaustif en IMPLEMENTATION + AC7.
- **Layout 6 colonnes** : min-width 280px → scroll horizontal dès ~1720px de board ; ergonomie à valider en VALIDATION_UI (largeur ajustable).
- **`completeSprint` face aux stages intermédiaires** : comportement des items non-`done` à la clôture à vérifier (pas de perte / statut inattendu).
- **Contraste dark theme** des 3 nouvelles couleurs de badge/colonne.

L'implémentation doit ajouter `dev` / `uat` / `golive` ou générer les options depuis l'ordre canonique des statuts, sinon l'édition manuelle d'un item à ces stages sera incohérente.

Refinements:
- Introduire une source d'ordre canonique réutilisable, par exemple `STATUS_ORDER = ['todo','doing','dev','uat','golive','done']`, utilisée par `renderBoard()`, `cycleStatus()` et idéalement la modale statut. Cela évite trois listes divergentes (`STATUS_LABELS`, board, cycle).
- Rendre les 6 colonnes par boucle plutôt que dupliquer 6 blocs HTML. La refonte est plus sûre si elle conserve `data-status` et `.board-col-body`, utilisés par le DnD existant.

L'implémentation doit surtout vérifier que 6 colonnes ne déclenchent pas de scroll horizontal page/body et que le scroll vertical WI-011 reste porté par `.board-col-body`.
- `completeSprint()` reporte déjà tout item `status !== 'done'` au backlog ([index.html:5231](../index.html#L5231)). Conserver ce comportement et le couvrir avec au moins un stage intermédiaire.
- Les nouvelles classes `.status-dev`, `.status-uat`, `.status-golive` doivent avoir des tokens clair + sombre, et `STATUS_LABELS[item.status]` devrait prévoir un fallback défensif pour éviter un badge vide si une donnée ancienne/altérée passe quand même.

Test gaps:

- Ajouter/couvrir DnD `uat -> golive` + persistance après reload (AC2).
